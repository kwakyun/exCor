# [ADR-001] 클라이언트 사이드 인메모리 예산 최적화 엔진 채택

## 상태
**승인됨 (Accepted)** - 2026-09-16

## 맥락 (Context)
여행지에서 예산을 입력하고 코스를 설계하는 사용자는 즉각적인 인터랙션 반응을 기대합니다. 슬라이더를 드래그하거나 이동 수단 옵션을 바꿀 때마다 서버로 API를 요청하고 응답을 기다리는 방식(전통적인 서버 사이드 계산)은 다음과 같은 한계가 있었습니다:
1. 부산 골목이나 해안가 등 통신 음영 지역에서 네트워크 지연(Latency)으로 인해 UI가 버벅거림.
2. 5인 팀의 초기 인프라 유지 비용 및 백엔드 서버(API Server, Database) 호스팅 부담 증가.
3. 데이터 변경 빈도가 크지 않은 정적 골목 명소 데이터(약 40~50개) 대비 과도한 서버 리소스 소모.

## 결정 (Decision)
**모든 예산 역산 및 스팟 조합 최적화 알고리즘을 브라우저 클라이언트의 메모리(TypeScript Service) 내에서 100% 실행**하기로 결정했습니다.

1. `src/data/busanAlleys.ts`에 정밀 검증된 5대 골목 권역 및 스팟 데이터를 정적으로 번들링합니다.
2. `budgetCalculator.ts`에서 다차원 조합 탐색을 클라이언트 JS 엔진으로 직접 수행합니다.
3. 스팟 변경(Swap) 시에도 서버 통신 없이 즉시 불변 상태를 갱신하여 10ms 미만의 반응 속도를 유지합니다.

## 결과 및 트레이드오프 (Consequences)

### 긍정적 영향 (Pros)
- **초저지연(Zero Latency)**: 예산 변경 시 1초 미만(평균 10ms 내외)으로 코스와 3-Pillar 게이지가 즉시 갱신됨.
- **오프라인 동작 가능**: 인터넷 연결이 불안정한 환경에서도 핵심 플래닝 기능이 온전히 작동함.
- **인프라 비용 제로**: 정적 호스팅(GitHub Pages, Vercel 등)만으로 대규모 트래픽을 감당할 수 있음.

### 부정적 영향 및 완화책 (Cons & Mitigations)
- **클라이언트 번들 크기**: 데이터가 수천 개로 늘어날 경우 번들 크기가 증가할 수 있음.  
  → *완화책*: 현재 5대 권역 스팟 데이터는 약 40KB 수준으로 gzip 압축 시 수 KB에 불과하며, 추후 수천 개 스팟 확장 시에만 동적 청크 로딩(`import()`) 또는 백엔드 캐시 레이어로 전환(Phase 2)함.
