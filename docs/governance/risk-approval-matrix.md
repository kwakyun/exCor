# 위험도 분류 및 사람 승인 정책 (Risk & Approval Matrix)

본 문서는 변경 작업의 성격과 영향 범위에 따라 위험도를 객관적으로 분류하고, 필수적인 사람 승인 조건을 정의합니다.

---

## 1. 위험도 분류 기준표

| 위험도 | 대상 예시 | 필수 통과 조건 및 승인 권한 |
|---|---|---|
| **Low** | • 단순 문구 수정<br>• CSS 스타일 및 UI 레이아웃 단순 변경<br>• 문서 수정 (README, docs) | • CI 검증 통과<br>• 사람 팀원 1인 승인 |
| **Medium** | • 일반 CRUD 기능 구현<br>• 일반 비즈니스 API 로직<br>• 일반 버그 수정<br>• 단위/통합 테스트 추가 | • CI 검증 통과<br>• QA 결과 확인 (Pass)<br>• 사람 팀원 1인 승인 |
| **High** | • 인증 및 인가 (Auth)<br>• 외부 결제/연동 API<br>• 데이터베이스 마이그레이션<br>• 공통 코어 API 계약 변경<br>• 관리자 권한 기능<br>• 환경 변수 구조 변경<br>• CI/CD 및 인프라 (Docker, K8s) 변경 | • 사람 집중 검토(Deep Review)<br>• Tech Lead 또는 코드 오너 승인 (필요 시 2인)<br>• 명시적인 Rollback 계획서 첨부 |
| **Critical** | • 결제 승인 또는 환불 핵심 로직<br>• 개인정보(PII) 수집/처리 방식 변경<br>• Secret 노출 및 권한 변경<br>• Production 운영 환경 직접 배포<br>• Production DB 테이블 삭제/파괴적 스키마 변경<br>• 인증 토큰 발급 정책 근본 변경 | • **자동 진행 즉시 중지**<br>• 사람의 명시적 사전 승인<br>• 관련 책임자(Security/PO) 필수 검토<br>• 별도의 운영/보안 검토 보고서 기록 |

---

## 2. Orchestrator 상태 운영 원칙

1. `status:ready`가 아닌 Issue는 Developer Agent에 개발을 배정하지 않습니다.
2. 설계 검토가 필요한 작업은 Architect Agent의 결과 및 사람 승인이 완료되기 전에 구현에 착수하지 않습니다.
3. CI가 실패한 PR은 사람에게 승인을 요청하지 않습니다 (수정 먼저 진행).
4. QA가 실패(`Fail` 또는 `Blocked`)하면 PR을 머지 후보에 올리지 않습니다.
5. `High` 및 `Critical` 등급의 변경은 빠른 머지 대상이 아니며, 사람 집중 검토 대상으로 표기하여 위험을 사전에 방지합니다.
