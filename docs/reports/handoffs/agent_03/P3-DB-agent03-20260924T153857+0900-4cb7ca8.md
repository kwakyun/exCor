## acceptance_results (STAMPS-DB-04의 verification_expectation 대조)

server-api.md에 명시된 5개 기대치를 모두 실제 pglite DB 위에서 테스트로 확인했다:

1. **재시작 후 중복 저장 없음** — `applyCanonicalBatch`가 `(chain_id, contract_address,
   transaction_hash, log_index)` PK 기준 `ON CONFLICT ... DO UPDATE`(upsert)로 이벤트를 저장한다.
   같은 구간을 두 번 적용해도 행이 늘지 않음을 테스트로 확인(`같은 (txHash,logIndex) 재수집해도
   중복 행이 생기지 않는다`, PASS).
2. **동시 요청 중 하나만 커밋, UNIQUE 위반은 conflict로 안전 처리** —
   `createAuthorizationIdempotent`가 선행 조회 후 INSERT하되 `isUniqueViolation()`으로 레이스를
   포착해 `replayed`/`conflict`로 분기. `stamp_authorizations_recipient_nonce_uidx`
   (`LOWER(recipient), nonce`) 위반 시나리오와 idempotency-key 위반 시나리오 둘 다 테스트로
   확인(PASS 2건).
3. **DB 장애를 null/not-found로 삼키지 않음** — 두 repository 모두 `isUniqueViolation()` 이외의
   에러는 전혀 catch하지 않고 그대로 throw한다(코드 검토로 확인; 별도 장애 주입 테스트는
   작성하지 않음 — remaining_risks에 기재).
4. **event/projection/cursor 한 transaction 커밋** — `applyCanonicalBatch`/`rollbackToBlock`
   전체가 `sql.withTransaction()` 콜백 안에서 실행된다.
5. **reorg 시 공통 조상 이전으로 rollback** — `rollbackToBlock`이 공통 조상 이후 이벤트를
   `canonical=false`로 표시하고, 각 (recipient,campaign,spot) projection을 남은 canonical
   이벤트 중 최고 block_number로 재계산하거나(대체 없으면 삭제) 커서/최근 블록창을 되돌린다.
   두 시나리오(대체 있음 / 대체 없음) 모두 테스트로 확인(PASS 2건).

## remaining_risks

- 실제 PostgreSQL 서버/드라이버(`pg` 등) 위에서는 검증하지 않았다. `@electric-sql/pglite`는 실제
  SQL 엔진(WASM 임베디드 Postgres 호환)이라 in-memory fake보다 강한 증거이지만, 네트워크 왕복
  지연·커넥션 풀·실제 동시성(다중 프로세스/커넥션 경쟁) 조건까지 재현하지는 못한다. 특히
  `createAuthorizationIdempotent`의 "선행 조회 → INSERT → UNIQUE 위반 시 재조회" 패턴은 단일
  커넥션/단일 프로세스 pglite 테스트로는 진짜 레이스(두 요청이 동시에 INSERT를 시도)를 만들 수
  없었다 — UNIQUE 제약 자체가 최종 방어선이라는 설계는 맞지만, 그 경로가 실제로 타는지는 실제
  동시 연결 환경에서 재검증 필요.
- `contract_address`/`recipient`를 항상 소문자로 정규화해 저장·조회한다(파일 상단 주석에 명시).
  in-memory 참조 구현과 동일한 "대소문자 무시 매칭" 효과를 내지만, 반환되는 `Address` 값은 항상
  소문자이고 원래 checksum 표기를 그대로 보존하지 않는다. 04/02의 상위 코드가 checksum 표기에
  의존한다면 문제가 될 수 있음 — 확인 요청.
- `applyCanonicalBatch`의 projection 갱신은 in-memory와 동일하게 "배치 내 처리 순서상 마지막
  값으로 무조건 덮어쓰기"이며 블록 번호 크기를 비교하지 않는다. 호출자(04의 `indexer.ts`)가
  항상 오름차순 블록 구간을 배치로 넘긴다는 전제에 의존한다 — 이 전제가 깨지면(예: 병렬 배치)
  잘못된 projection이 남을 수 있다.
- P3-DB는 여전히 `depends_on: P3-01(완료, 01 수용 대기), P1-06(미착수)`이다. P1-06(실제 DB
  마이그레이션 적용/연결 부트스트랩)이 없는 상태이므로, 이 handoff는 "레포지토리 구현 자체의
  정확성"을 pglite로 증명한 것이지 프로덕션 DB에 실제로 연결해 운영했다는 뜻은 아니다
  (P1-05/P2-01과 동일한 원칙 — provisional 작업, accepted_handoffs 등재는 01의 판단).
- migration은 순수 추가(`CREATE TABLE`)라 파괴적 변경 없음. 롤백(DROP) 스크립트는 아직 작성하지
  않았다.
